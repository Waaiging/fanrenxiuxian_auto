## 具体损失与代码问题

### 主号最后一个结束回执被误算成命中

主号第 16 次 `/hit` 收到 HTTP 成功，但正文只有：

```json
{"bossHp": 0, "damageYi": 0, "perfect": false}
```

其中没有 `deltaMs` 或服务端蓄力时长。最终结算明确给出 `hits=15`、`realtime_hit_count=15`、`sample_count=15`、`perfects=14`。旧代码把 HTTP 成功统一记为命中，并且结算时没有核对命中字段，因此历史本地字段显示 16，四号相加会错误得到 63。

修复后，这种明确的结束回执独立计入 `ended_hit_count`。它不算命中、不算网络失败，也不冒充尚未发送的跳过动作；真实释放仍保留在 proof。真正造成伤害的最后一击，以及带实际攻击计时的零伤害回执，仍按攻击处理。最终用服务端合法的 `hits`（缺少时使用 `realtime_hit_count`）与 `perfects` 核对统计，并保留来源及差异。

此次不修改已完成的历史 state；今天主号应按上述服务端结算解释为 15 次。

### Waaiging 第 14 击本地唤醒迟到 1.875 秒

该窗口提前 1798ms 取得；出手预留落盘仅 7ms，蓄力请求 181ms。蓄力回执返回于战斗第 74066ms，原计划第 74888ms 释放，实际醒来已是第 76763ms，本地蓄力变成 2878ms。程序正确阻止了过期 `/hit`，最终记录 `local_window_missed`。

代码检查发现一个可独立复现的问题：可中断等待先计算剩余时长，再创建执行 `sleep(剩余时长)` 的子任务。若循环在子任务启动前停顿，子任务还会完整睡一次旧时长，扩大延误。现在改为在让出循环前登记绝对截止时间；模拟 421ms 与 1875ms 的循环停顿，截止后均不会再追加旧等待时间。停止信号、任务取消、连续战斗及并发等待继续受回归覆盖。

这证明修复能消除追加等待，并不能证明它解释了今天整段 1.875 秒。13:40 可用内存约 141MiB；覆盖战斗的 13:40–13:50 系统采样仍有 8.39% I/O wait、约 452/348 页每秒换入/换出。内核日志在取证区间未检出相关异常，现有证据没有当时的线程栈，不能把这次停顿唯一归因于换页、GIL 或某个后台任务。

### 小号首击的慢蓄力回执污染后续时长

小号第 1 击的蓄力请求耗时 981ms，正常约 190ms；本地按住 987ms，服务端票据只蓄力 201.1ms。虽然到达偏差仅 19.8ms，这一击仍被服务端判为普通命中。

以该次真实回执回放，首击仍保留“普通命中”，下一击计划保持 1000ms。正常请求下持续出现的蓄力偏差仍会调整后续参数。此修复避免把瞬时延迟带到后续窗口，不宣称能补回今天的伤害或保证首击转为完美。

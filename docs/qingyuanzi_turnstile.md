# 青元子全自动验证研究记录

2026-09-07：已打通真实浏览器回调与四账号自动队列交接，实际战场 `/begin` 的服务端验票仍待下一场确认。

## 观察与结论

| 检查 | 结果 |
| --- | --- |
| 原人工交接 | 历史请求等待 180 秒后超时，没有收到浏览器令牌；Dashboard 复制按钮缺少对应函数 |
| Playwright 控制浏览器 | 本次有头、无头实验均收到 CF `600010` |
| 原生 Chrome + 本机 CDP | Windows、WSL 与 VPS 均获得真实 Turnstile 回调 |
| VPS 冷启动后连续四次验证 | 29.64、11.14、11.24、10.78 秒，4/4 成功 |
| VPS 四账号隔离队列 | 最后一个账号在 64.51 秒收到令牌；全部只取用一次，令牌文件清零，浏览器退出 |
| 有效 Mini App 授权 + 无效战场凭据 | 服务端先返回 `boss_token_missing`，无法借此验证后续 CF 验票 |

上述浏览器实验说明当前环境下全自动回调可行，不能据此保证后续 CF 策略不变，也不能将回调成功等同于游戏服务端接受。

## 实现

`world_boss_browser.py` 使用独立的原生浏览器实例，打开官方青元子页面，读取页面提供的 site key 和 action，等待控件进入交互阶段后完成一次控件点击。令牌完全来自 Turnstile 回调；没有伪造令牌，也没有修改浏览器指纹。Chrome 的调试连接仅在本机使用，Telegram 会话和 Mini App 授权不进入浏览器。

四账号共用一个串行验证器，避免小内存 VPS 同时启动多个浏览器。队列进程锁保证只有一个验证器；首次尝试优先于重试，每请求最多两次自动尝试。空闲 20 秒后关闭浏览器。`start_all.sh` 的 `xiuxian:5` 启动常驻验证器。

游戏 worker 遇到 `turnstile_required` 等错误后创建临时请求，自动验证器提交一次性令牌，原 worker 取用后继续 `/begin`。服务端返回后另记 `accepted` 或 `rejected`，避免将“令牌已取用”误报成“入阵成功”。网络重试不重复使用已经发出的令牌。

同时修复了开战校时：原流程会把约 30 秒浏览器等待算进 RTT，进而让攻击提前数秒。现在仅使用最终成功 HTTP 请求的往返时间和收包时刻，排除验证等待、前序失败请求与本地回执落盘时间。

## 验证范围

- 64 项青元子、令牌队列、自动验证器和 Dashboard API 定向测试通过。
- 28 项受限账号、进程管理和群可见性测试通过。
- 浏览器 UI 检查覆盖复制按钮、弹窗来源校验、回调单次提交、服务端结果回执、提交失败重试、桌面和手机布局，无页面 JavaScript 错误。
- 全量 974 项测试存在 25 个失败和 9 个错误；用修改前文件复跑失败项，得到相同结果，属于已有问题。
- 真实 CF 令牌没有写入报告、日志或账号状态；队列仅短时保存并在取用时删除。

## 下一场确认

Dashboard“青元子安全验证”应依次出现自动验证、令牌取用与入阵结果。只有 `/begin` 返回成功才显示“入阵成功”。若服务端拒绝，查看安全错误码以及账号 `world_boss_events[].identity_results[].diagnostics` 中的交接记录；不要重放旧令牌。

手动验证入口保留为故障备用。日常自动流程不要求打开 Dashboard、复制脚本或手动粘贴令牌。
